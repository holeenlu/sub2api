# Cloud RPC 全链路复核与修复（2026-10-26）

## 范围与判定基准

审查基线为 main 1b88a4afaf5a79323c8e3170635dc07e0a55054f。以原生网关的鉴权、模型权限、调度、取消、错误和账务规则为准；Cloud 只承担上游 RPC 映射、执行归属和客户端工具等待所需状态。本轮不启用账务 v2 写入，不新增授权、模型名单、验证门禁、产品配置或自动协议切换。

按“未发送、已发送且接受未知、等待客户端工具、已确认终态”分析各副作用边界。请求可重试不等于上游执行可重放；客户端响应完成不等于 Cloud turn 已结束；用量未提供不等于零用量。

公开 RPC 契约来源：[OpenAI App Server](https://learn.chatgpt.com/docs/app-server)。公开文档不代替特定 Cloud 主机的能力实测。4 MiB 是既有真实主机探针确认的单消息解码边界，不是整个会话上限。

## CPR 生命周期对照补强

本次基线 `ec0222f3494a8def8427e969bce4f6eea7fa2e78`；只读参考 CPR `1db8b0e319431717611e3e30ae1a2d3b371de86a` 及其插件子模块 `a02c7eacd173119165105f6e5d52220155bd4cb3`（Apache-2.0）。这两个公开快照未发现等价的 Codex Cloud App Server：CPR 的插件 RPC 是宿主与子进程的 framed stdio 协议，本项目是 Cloud WebSocket 上的 App Server 消息。借鉴其 OpenAI WebSocket pump 先排空已接收数据再结束、插件 RPC 先撤销执行资格的生命周期原则，沿本地 Go owner 实现，不引入 Rust 插件运行时或宣称直接移植了 CPR Cloud。

| 边界 | 原问题 | 修复 |
| --- | --- | --- |
| 远端断线 | transport 清空 FIFO；actor 的独立 failure 通道还可抢在完成/用量前被处理 | 区分远端断线与硬终止；已接收事件和终止通知共用一条有序通道，排空后报断线；连接立即停止写入和复用 |
| RPC 回包 | 已确认回包与随后断线同时就绪时，select 可返回断线 | pending 锁内发布回包；断线分支优先读取已确认应答，调用取消及硬失败仍终止，不重放 |
| 工具交接 | 已观测 owner 失效或连接关闭后，排队工具仍可向客户端发布 | 工具接纳及发布检查 owner、当前请求取消/期限和连接状态；终态刷新消息时禁止再交出工具；既有用量/终态按原规则结算 |
| RPC ID | 原始 JSON 字节比较漏掉等价转义字符串 | 复用 cloudRPCIDKey 比较语义，数字与字符串仍区分，回复保留原始 ID |
| 停止/压缩续接 | 单独错误通道使消费者只能等超时 | 同一有序终止通知覆盖停止和中断确认等待；channel 关闭也立即退出；ACK 不等于终态 |

## 客户端权限与 Cloud 主机上下文（2026-10-27）

### 根因与修复边界

`cloudThreadParams` 把 Cloud 主机执行权限设为 `permissions=":read-only"`、`approvalPolicy="never"`，但没有关闭 App Server 默认的权限和环境提示。客户端工具在本机执行，Cloud 主机权限却作为另一段 developer 权限说明/环境上下文进入模型，因而可能覆盖本机 `workspace-write` 或 `danger-full-access` 的含义，造成“当前只读、禁止提权”的错误判断。

本轮只在同一个 `thread/start.config` 中设置 `include_permissions_instructions=false` 和 `include_environment_context=false`。前者停止注入 Cloud 主机的权限/审批说明；后者停止注入 Cloud 主机的文件系统、目录等环境信息，避免从另一个提示入口再次带入只读限制。客户端输入中的权限说明、审批要求和环境文本仍原样保留，未按文字内容提取或提升实际权限。
