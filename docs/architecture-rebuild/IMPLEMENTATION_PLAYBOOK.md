# 重构开发启动手册

日期：2026-10-25。用途：把已有设计转换为可领取、可审查、可接手的开发工作。
当前仍是开发前资料阶段；本手册不启动业务编码，也不证明任何运行场景已经通过。
收到后续实施指令后使用本流程；实施状态和精确依赖只读[work-items.json](work-items.json)。
本文件提供操作顺序，不复制合同、语言规范、全部任务或交付政策。

## 1. 找到唯一资料与责任人

| 要回答的问题 | 唯一依据 | 负责更新的人 |
| --- | --- | --- |
| 做什么、哪些行为不可改变 | [REQUIREMENTS](REQUIREMENTS.md)、[DECISIONS](DECISIONS.md) | 集成者协调需求与决策责任人 |
| 模块怎么分、接口如何消费 | [ARCHITECTURE](ARCHITECTURE.md)、[CONTRACTS](CONTRACTS.md) | 对应合同owner |
| 前端结构、品牌与配置边界 | [FRONTEND_ARCHITECTURE](FRONTEND_ARCHITECTURE.md)、[BRANDING](BRANDING.md) | 前端集成者及相应领域owner |
| 谁能改哪些文件、依赖是否满足 | [任务JSON](work-items.json)；[工作包视图](WORK_PACKAGES.md)供阅读 | 集成者单写 |
| 语言写法、检查与局部例外 | [CODING_STANDARDS](CODING_STANDARDS.md)及其语言级细则入口 | 规范owner维护，worker消费 |
| 什么证据有效、旧实现何时删除 | [VALIDATION](VALIDATION.md)、[MIGRATION](MIGRATION.md)、[RETIREMENT](RETIREMENT.md) | 切片owner与评审者 |
| 如何交接、何时可交付 | [COLLABORATION](COLLABORATION.md)、[READINESS](READINESS.md)、[现行交付规范](../CHANGE_DELIVERY.md) | 集成者及交付责任人 |

首次接手从[README](README.md)进入；随后读任务JSON列出的必读资料及本包实际消费的合同。
一个人可承担多个角色；同一共享文件仍只能有一个实际写者，不因多个子智能体而放宽。
发现资料冲突先指明来源和受影响任务，由其owner修正唯一来源；本手册不得变成第二份状态表。

## 2. WP-00：冻结实际实施输入

集成者在开发开始时记录以下事实；沿用[BASELINE](BASELINE.md)和[source-inventory](source-inventory.json)，不另建平台。

1. 记录实际仓库、工作树、分支或detached状态、HEAD及工作区差异；区分已提交输入与他人未完成改动。
2. 核对本轮消费的源码文件和指纹；历史设计SHA只说明资料来源，不能自动充当当前开发基线。
3. 记录合同、编码规范、前端设计和品牌设计的实际版本；每个领取任务绑定同一组已核对输入。
4. 核对现有依赖清单、锁文件、构建与检查配置，并记录实际Go、Node、pnpm等相关工具版本。
5. 不因为版本较旧自动升级来源或依赖；工具链不匹配先确认现有项目要求及受影响检查。
6. 核对有效客户端、路由、回调、存储键、数据读者和代表夹具；真实上游材料缺口登记至对应验收项。
7. 区分代码可直接推进的工作与缺证据的切换；只阻断受影响部分，不让全部领域等待同一外部条件。
8. 确认任务写集及共享文件owner；将领取基线和证据位置写入现有任务与交接记录。

WP-00完成的是输入核对；不要求预先通过尚未开发的全部业务场景，也不触发生产访问或数据迁移。
既有验证仅在相关源码、依赖、生成输入、命令、工具链和环境仍匹配时复用，并标明历史执行时间。

## 3. WP-01：先形成可消费合同

WP-00验收后，合同owner把CT设计落实为最小共享值对象和消费端口，按JSON授权写集落地。
需要修改消费方或公共声明之外的路径时，由集成者先明确归属；不能用目标目录不存在扩大写权限。

- 固定身份、单位、零值、unknown/absent区别、错误类别、资源寿命及取消责任，遵守CONTRACTS。
- 以实际编译和必要的定向行为检查证明类型可消费；设计签名、空接口或伪造实现不算可编译合同交付。
- 合同不承载平台分支、全局service实体或第二套v2类型；端口位置按实际消费者及架构依赖确定。
- 交接公开出口、实际版本、适用检查结果和消费者名单；真实adapter或上游验收仍归后续任务。

该阶段验收的是合同产物，不是整个网关已经实现；下游读取验收产物后才开始依赖它的实现。

## 4. 首个前端切片：WP-28基础与WP-29切换

这是两个验收层次，不把身份业务反向塞进基础包，也不让最终装配成为首次接线的前置。

| 阶段 | 谁执行 | 产出与验收边界 |
| --- | --- | --- |
| WP-28基础 | 唯一shared写者 | 消费已验收合同，交付可编译HTTP/令牌协调、session读取合同、公开设置投影及UI/i18n技术基础 |
| WP-28评审 | reviewer与集成者 | 按JSON的基础特例检查接口、依赖与定向行为；可accepted，但明确运行入口尚未切换 |
| WP-29领域实现 | identity/keys写者 | 在JSON规定前置验收后完成身份安全、API Key领域及公开出口 |
| WP-29纵向集成 | 同一前端集成者 | 将WP-28基础与身份领域接入启动、生命周期和路由，并删除本切片已替代的旧入口 |
| WP-29验收 | reviewer与集成者 | 核对真实消费、身份/范围失效、刷新与有效登录合同；未接入或旧入口未处理不能accepted |

WP-28的可编译基础验收不能表述为“新前端已上线”，也不能单独发布未接入的新架构。
WP-29运行切换要包含WP-28列出的共享入口变更；worker交补丁建议，集成者执行受保护路径修改。
删除当前仍被其他领域使用的共享旧文件，要等最后消费者退出；登记具体读者和退出条件，不留永久wrapper。
其他领域在自身JSON依赖满足后可以并行实现，无需人为新增WP-29为全部任务的代码开发依赖。
需要新身份/应用运行基础的领域接入，由同一集成者安排在该基础切换之后，或纳入同一次明确的集成批次。
WP-21负责最终跨域组合与遗留收敛；不能以等待WP-21为由推迟所有领域的首次接线。

## 5. 后续并行波次怎么安排

以下只解释调度顺序；能否领取始终逐项检查JSON的depends_on、写集和验收记录。

- 合同后：纯协议、access、账务、目录与host等在各自前置满足时并行；session和routing还要等待access。
- 原生闭环：execution等待所消费端口，native adapter按自身前置推进，再由集成者完成原生垂直切片。
- 控制与前端：控制面前置满足即推进；WP-28无需等到其他provider完成，领域包等待各自控制与基础合同。
- 扩展能力：原生完整切片后，模式、平台、媒体和实时worker在分离目录并行，遵守各自额外依赖。
- 串行汇合：共享旧入口、Wire、路由、生命周期与跨域页面由集成者接入；每个切片处理本次替代路径。
- 最终收敛：部署品牌参数先于其依赖集成完成，随后旧路径总核对、整体风险验收，再按现行政策交付。

跨领域读对方公开合同，不直接修改对方实现；精确依赖不足时先修JSON，不能靠聊天口头跳过。
并行数量由稳定合同、实际写集和可评审能力决定，不把“所有agent同时启动”当作效率指标。

## 6. 任务状态的操作判定

使用JSON现有状态词；以下是[协作协议](COLLABORATION.md)的领取与验收操作说明，不建立新状态系统。

| 状态 | 可以进入的条件 | 记录责任 |
| --- | --- | --- |
| planned | 已规划但尚未确认全部实施前置 | 集成者保留事实，不自动派发 |
| ready | depends_on所需产物已accepted且适用范围清楚；实际基线、合同、写集、验收方法无阻塞 | 集成者核对；正式领取时登记唯一assignee |
| in_progress | ready后已领取，owner已确认输入和边界，开始实施 | 集成者登记；worker提供实际进展 |
| review | 本包产物和实际diff齐备，适用检查已执行或明确缺口，交接可复核 | worker提交；review不代替验收 |
| accepted | reviewer核对风险证据，集成者确认本包outcome、消费者与清理要求已满足 | 集成者更新JSON并关联验收记录 |
| blocked | 已确认的合同、依赖、环境或证据缺口阻止本包必要步骤 | 写明阻塞对象、owner、已完成部分和恢复条件 |

未运行的必要验收不能靠“无报错”转为accepted；与本包无关的外部缺口不应阻断已明确工作。
WP-00/01按其输入或合同产物验收；WP-28按JSON明示的可编译基础特例验收。
普通可运行切片仍须完成集成与相应旧路径处理；该特例不能推广为“所有未接入新包都可accepted”。
review发现需要修改则回到相应实施或blocked状态，保留原有证据及变化原因，不覆盖历史结论。

## 7. 单写者集成、变更与接手

领取时用[HANDOFF](templates/HANDOFF.md)及现有worker提示模板约定输入，不另发明一套交接字段。
每个worker只改write_paths；legacy_read_paths是只读锚点，integration_paths由指定集成者处理。
共享合同、app/shared、根入口、路由、锁文件、生成装配及迁移等保护范围以协作协议为准。
同一工作树即使文件分离，stage、索引和分支切换也必须串行；不能收进其他任务未完成修改。

1. worker提交实际补丁、消费者影响和旧路径处置建议；集成者对照固定输入审查归属。
2. 共享改动由唯一owner执行，相关消费者一起检查；不能先合临时兼容层，把真正收敛推到以后。
3. 发现合同变更时列出CT、失败场景、最小调整和消费者，再由合同owner更新唯一声明与版本。
4. 源码或合同漂移时保留diff，确定受影响部分后再基线化；不得reset他人工作或只刷新版本号。
5. 阻塞任务留下可复现事实和恢复条件；其他不依赖它的任务继续，不绕过权限或账务约束凑进度。
6. agent中断或换人时，集成者读取实际文件、执行结果和未提交差异；聊天“完成”不能替代证据。
7. 接手者延续同一WP、剩余写集和验收，不另起平行实现；owner转移由集成者串行登记。

已授权工程细节由owner直接处理；涉及明确产品行为或独立生产操作时按现行授权边界处理。
本手册不要求额外逐项用户审批，也不授权worker推送正式分支、发版、部署或生产迁移。

## 8. 证据必须说明实际验证到哪一层

证据等级和具体场景以[VALIDATION](VALIDATION.md)为准；下表仅供填写交接时辨别环境。

| 等级 | 证明范围 | 不能外推为 |
| --- | --- | --- |
| U / S | 单测或本地替身组合中实际覆盖的行为 | 真实存储、客户端或上游通过 |
| R / M | 隔离真实DB/Redis，或多个独立网关进程的实际行为 | 真实上游或生产已验收 |
| C / P | 指定版本真实客户端，或指定模式/账号/传输真实上游 | 另一端为替身的部分也已验证 |
| O | 指定品牌、部署SHA、revision和时间窗的线上事实 | 所有版本、平台和品牌均通过 |

这些等级表示验证环境，不是单一分数；有P不能替代R/M账务、租约或跨进程证据。
每份结果关联WP/REQ/CT/AT、实际源码与输入、命令/cwd、环境、时间、结果和限制。
Skip、零命中、测试仅存在、进程退出0都不能单独证明场景成功；未运行记not_run，未采集记not_collected。
只执行实际风险需要的现有检查；资料修改做静态检查，不为形式完整运行全应用构建或新增验证平台。
脱敏后保留最小可复核材料；任何真实上游调用和生产操作仍受现行授权与数据边界约束。

## 9. 开发完成与交付前核对

集成者按[ACCEPTANCE_RECORD](templates/ACCEPTANCE_RECORD.md)逐个记录实际完成情况。

- 需求与合同：实际行为满足本包outcome；签名一致不代替状态、取消、幂等、安全和账务语义。
- 消费与清理：真实入口和消费者已切换；废弃实现、字段、文案、配置与专属测试按清单同次处理。
- 有效保留：仍在使用的URL、数据读者或合同有依据及退出条件；历史数据处置与代码删除分开说明。
- 证据与复核：适用风险有足够等级的真实结果；复用证据说明输入匹配，缺口与限制明确归属。
- 范围与资源：无越界修改；分别统计业务/测试增删及接口、配置、执行路径变化，登记任务资源收尾。
- 交付边界：源码提交推送、发布、部署与迁移分别报告；正式交付读取现行政策，不在本手册复制分支命令。

只有对应验收完成才更新JSON状态与READINESS；文档准备、代码完成和上线准备始终分别判断。
资料阶段的语言细则、目标目录、工作包及场景都是实施输入，不是已实现功能或已通过测试的回执。
