# sub2api 项目身份与品牌配置规范

版本：1.0。需求确认日期：2026-10-25。状态：开发合同与源输入记录；独立分支已开始实施，已完成范围及未验收项见IMPLEMENTATION。用户明确要求统一技术项目名称sub2api，清理上游广告/赞助等无关推广，品牌部署时自定义镜像/容器标识，网站Logo、品牌名和API链接等通过设置配置。

本要求替代目标设计中“靠品牌分支分别维护代码/资产默认值”的假设。**目标是一套代码和按服务角色构建的制品，多份独立部署配置。** 当前 `NewAPI` 是唯一维护和交付分支；`main`/`TapModels`/`tokensavy` 仅作为历史和差异参考，本文件不删除其历史分支、标签或Release，也不擅自改变其既有权限。

## 1. 三种身份分别归属

| 层级 | 决定什么 | 唯一负责处 | 不影响什么 |
| --- | --- | --- | --- |
| 技术项目身份 | 项目名称sub2api、版本/构建信息、项目文档和代码元数据 | 集中的项目身份/构建元数据；复用现有构建与启动装配 | 不从运营品牌名推导协议、授权或数据归属 |
| 部署身份 | 镜像引用、编排项目、可选容器名、网络/卷挂载、域名与入口 | 部署配置、环境和编排工具 | 网站设置不能改Docker资源、镜像仓库凭据或更新信任源 |
| 网站品牌 | site_name、site_logo、站点文案、公开API链接、文档/联系信息 | 现有SettingService及经筛选的public settings投影 | 不改变业务规则、API路由、管理API鉴权或上游请求目标 |

默认按一个部署实例使用一份网站配置设计。多个品牌使用独立部署配置，不新增单实例按Host动态切换多租户的系统；如后续需要该能力，另定义身份、缓存、数据和权限合同。

## 3. 网站设置合同

### 3.1 复用字段

| 现有字段 | 目标含义 | 默认/变更语义 |
| --- | --- | --- |
| site_name | 运营品牌显示名 | 新安装未配置时回到中性项目名sub2api；显式保存值优先 |
| site_logo | 网站Logo，并复用既有favicon更新机制 | 未配置时使用随项目提供的中性本地资产；不默认请求上游赞助/历史品牌资源 |
| site_subtitle | 站点副标题 | 中性、与功能相关的默认说明；不能夹带广告和另一品牌名称 |
| api_base_url | 用户文档、复制示例及客户端配置中公开的网关API基础地址 | 明确是否含/v1等路径，复用当前使用者合同；不直接覆盖浏览器管理API client或provider上游地址 |
| doc_url | 本部署面向用户的文档入口 | 可配置有效链接或使用中性项目文档；缺省时不指向历史品牌域名 |
| contact_info | 运营方联系信息 | 通过已有类型/渲染合同输出；不默认携带原作者商务推广 |

附加主页、页脚、帮助或法律主体信息，先核对现有设置/导航字段能否承载；确有缺口再登记具体字段、读写位置、公开范围和兼容条件。不要新增可执行脚本、任意样式代码或一个能覆盖所有配置的branding map。

### 3.2 读取和更新

- SettingService为配置权威，公共DTO只投影允许公开的字段；后台凭据、镜像仓库密码、更新令牌、内部地址和签名信息不进入public settings。
- 后端启动注入与公共设置API使用同一有效值计算，前端复用现有app store与branding helper。构建时仅有中性兜底，不能保留每品牌的另一份值。
- 保存复用现有管理权限、审计和设置失效机制；不同配置域的revision按CT-08处理，不强迫旧客户端凭空增加字段。
- 标题、Logo/favicon、侧栏、登录页、首页、错误/空状态、用户手册、复制的API示例、邮件与通知、支付描述、供应商门户分别列出消费者。显示同一个有效品牌，不把改名交给页面逐个写条件。
- 新配置加载前只显示中性信息或经过当前实例确认的配置，不能短暂显示另一品牌。缓存按当前实例和设置版本隔离，改Logo后处理浏览器缓存与清空行为。
- 文本使用i18n参数和安全渲染，不能对整个页面、协议body或用户内容全局替换品牌字符串。

### 3.3 地址必须分域

| 地址 | 用途 | 品牌设置能否直接改变 |
| --- | --- | --- |
| 公开API基础地址 | 面向用户展示/复制的网关地址 | 可以，通过api_base_url及其既有合同 |
| 管理/控制台API地址 | 浏览器携带登录态调用控制面 | 不能因修改api_base_url自动迁到任意第三方；独立部署来源与可信目标配置 |
| 上游provider地址 | 转发模型请求、使用账号凭据 | 不可以，继续由资源/代理/出口与provider配置控制 |
| 登录回调/支付Webhook | 第三方注册合同、签名和回调入口 | 不随site_name/Logo更换；按对应授权配置单独处理 |
| 更新仓库/镜像来源 | 软件发布、升级、回滚与摘要校验 | 不从网站品牌名或域名推断，继续采用独立可信发行配置 |

本区分不增加产品验证开关，而是防止一个公开展示字段获得不属于它的权限。

## 4. 部署身份与制品

### 4.1 目标部署参数

以下是拟定的中性部署入口，不代表当前Compose已经实现。具体模板替换由WP-22/23/26完成，不在本轮更改运行配置。

| 参数/入口 | 责任 | 约束 |
| --- | --- | --- |
| APP_IMAGE | 当前服务角色使用的完整镜像引用 | 部署者可指定仓库、镜像名和版本/摘要；代码不能硬编码品牌镜像 |
| COMPOSE_PROJECT_NAME或编排器等价项目标识 | 部署资源的项目范围 | 与网站site_name分离；改名必须核对网络、卷与外部依赖 |
| APP_CONTAINER_NAME（可选） | 单实例部署需要的显式容器名 | 未设置时模板省略固定容器名；多副本不能依赖应用内写死的唯一容器标识 |
| 持久卷/挂载、网络和端口 | 已有部署模板与运维配置 | 显式保留旧数据映射；不随Logo、展示名或镜像tag自动改名 |
| 门户/主站外部地址 | 对应部署角色的可信入口 | 复用现有独立门户机制，不让公开API展示字段替代管理连接配置 |

旧KDAN_IMAGE及其他品牌变量如何导入中性入口，需要列出实际使用者、版本和退出条件。只能有一次明确的解析/迁移归属，不能永久并存三套品牌if/else。旧变量存在不授权静默更换镜像或停止现有实例。

### 4.2 同一制品支持多个品牌

相同服务角色与版本在不同品牌部署时，品牌差异仅来自部署参数、持久配置和已配置资产。镜像可以使用部署方自定义引用/别名，但必须保留真实版本、摘要与来源可追溯性；不能把重命名镜像当作新的代码版本。

主服务与独立供应商门户若因职责已有不同制品，可以保留功能角色划分；不能为了品牌分别编译同一角色。源码和构建中的品牌选择分支、固定域名及标识副本在迁移完成后删除。

升级器、回滚示例、运维脚本和门户更新说明必须读取实际部署配置，不继续从BRAND_NAME或RELEASE_DOCKER_IMAGE猜镜像、容器、数据卷和发布渠道。网站设置不能执行宿主命令或操纵Docker。

## 5. 广告 赞助与无关推广清理

### 5.1 清理对象

- 上游作者/第三方赞助名单、赞助Logo墙、购买/注册导流、返佣推广链接和无关广告卡片。
- 与这些内容专用的组件、路由、图片/静态文件、翻译键、默认导航、种子设置和安装/文档模板。
- 为展示这些内容而增加的专用请求、统计或外链资源；先证明归属，不能误删共用资源或正常业务能力。
- 发布包、README/部署引导、四语用户文档及新安装默认界面中的同类内容，后续同步继续以此为内容边界。

当前已不存在的对象记录“已覆盖”，不凭旧上游文字再造一套删除实现。关键词和域名扫描用于定位，最后以用途、调用链和制品可达性判定。

### 5.2 保留对象

LICENSE、NOTICE、原始许可证、必要版权/来源记录、第三方依赖署名和历史迁移不属于广告清理对象。不得以品牌统一为由修改这些原文来隐藏来源。

既有套餐、充值、支付、运营公告、用户推广返佣或供应商业务若属于明确产品需求，继续保留；清理的是上游无关推广内容，不是按“推广/赞助/充值”关键词删除整个业务模块。新增部署默认不预置原作者商业推广，也不自动新增广告位。

### 5.3 清理证据

每项记录：旧内容位置、实际消费者、公开入口/制品、共享与专属资产、删除或保留理由、对应REQ/BR、语言与测试更新、是否有历史数据读者。最终要验证空白安装、已配置安装及打包产物，不以隐藏界面或搜索无命中宣称完成。

## 6. 升级 与未来更名

### 6.1 现有品牌迁移

1. 读取现有显式设置及当前生效fallback，记录每个部署实际显示名称、Logo、链接、镜像、容器和挂载。不得凭分支名称猜配置。
2. 显式保存值始终优先；依赖旧编译fallback的存量部署，先明确一次性导入/持久化方案，再删除fallback。新安装默认中性，不能继续自动识别成历史品牌。
3. 映射部署参数和旧数据挂载，确认升级仍读取同一数据库、卷和必要状态；改名不等于重建或删除数据。
4. 同一垂直切片验证后台保存、公共投影、首屏、各消费者、独立门户与邮件/支付展示，并删除旧品牌常量、重编译选择器和仅供推广的实现。
5. 用户已指定 `NewAPI` 为唯一维护分支；现有三分支/渠道不再作为本项目同步和交付目标，重构改动不向它们传播；收敛后的代码、制品和部署profile关系在WP-26明确，不通过本次文档编辑删除历史分支或发布新镜像。

### 6.2 更名不变的东西

改网站显示品牌：只改网站设置。改镜像/容器等部署名字：只改部署配置并验证数据与运维映射。改技术项目名称：修改集中项目元数据，并检查仓库/module/import、二进制/包名、构建、安装文档和外部合同。

技术更名不承诺只改一个网站字段即可完成。历史数据库表/列、Redis键、幂等request/key、OAuth client_id、Cookie与签名协议、第三方原生身份等是否可改，必须单独核对实际读取者和迁移；不能对仓库中的sub2api或旧品牌名执行无差别替换。

品牌名不得成为账务键、租户/用户隔离、owner epoch、存储namespace或更新信任身份。必要的部署/实例标识保持稳定，不随site_name变化；已有持久标识按历史合同迁移而非偷偷重置。
