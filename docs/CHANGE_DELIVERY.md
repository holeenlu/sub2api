# 需求归属与提交、推送规范

适用于新增功能、修复、重构、合并需求及其交付。当前采用 `main` 作为 KDAN 品牌主分支、`TapModels` / `tokensavy` 品牌派生和 `upstream-base` 官方基线的结构。目标是先判断改动归属，再选择提交位置和发布目标；当前检出的分支只是工作现场，不能作为归属依据。

## 当前分支结构

默认同步来源（2026-10-24 最新调整，取代此前三源范围）：Wei-Shaw/sub2api `main` 为完整官方基线；ranxi2001/sub2api `production`、QuantumNous/new-api `main`、zyycn/codex-proxy-rs、dofastted/vm2api `main` 为四个选择性来源。Codex Proxy RS 每轮核实实际默认分支，五个来源分别固定 SHA；选择性来源按本地 Go/Vue 架构评估适配，不整分支合入或新增平行网关。MACOS-DO/sub4api 仍不默认拉取或审查新增提交，也不推进其 reviewed 水位，明确点名时才评估。来源范围与取舍记录由现有 Skill 来源索引及适配文档维护；已参考 SHA 不代表整仓已核查，新增或恢复默认来源不清空既有核查证据。已有有效功能、署名及历史迁移保留。

vm2api 来源为 `dofastted/vm2api`，不是定制仓库 `holeenlu/vm2api`；复用本地源码检出时只读取核实后的来源提交，不改动其工作区、分支或发布状态。本技能只交付 Sub2API，不调用另一个项目的同步/部署流程。优先对照 [六项能力](vm2api-completion-2026-10-21.md) 和 [账号遥测](ACCOUNT_TELEMETRY.md)，比较实际行为和局部核查范围，不重复移植、不自动引入 Node/VM/guest/独立调度运行体系。复制或适配源码、模板、静态资产前核实固定版本的许可证、NOTICE 和适用授权；vm2api 当前已查版本包含非商用限制及书面商用授权要求，纳入来源不等于取得该授权。许可待确认项与技术取舍分开记录，不以改写语言规避许可，也不擅自清除已有功能。

普通新增、修改、修复及提交推送保持当前已核对的官方基线，只处理本次需求和必要关联改动，不附带来源同步、依赖升级或无关修复。只有用户明确同步上游时才审查来源增量；整合新发布的本仓库改动不等于授权同步新上游。已知独立缺口另记，不悄悄扩大本轮范围。

三个品牌均以同一个已核对的 `Wei-Shaw/sub2api main` SHA 为直接父提交，各自只保留一笔完整定制提交。共享逻辑先在 main 审查与验证，再将共享变更与各品牌实际差异做三方文件树整合；正式历史不保留 merge 节点，也不让品牌重新接入旧 main 历史。品牌专属需求只更新对应品牌。`upstream-base` 只记录官方基线，不承载定制；完整结构见 [分支结构](BRANCH_STRUCTURE.md)。

自 2026-10-03 起，代码推送仅限本仓库 `holeenlu/sub2api` 的 `origin/main`、`origin/TapModels`、`origin/tokensavy`；不再推送 `erwinlin/main` 或其他仓库。推送目的地不能由跟踪关系推断，一律写全源、目标 ref。旧文档、历史整合记录、已保存检查点中的旧目标不能覆盖现行规则。

`git cherry` 的 `+` 表示未找到等价补丁，可能来自品牌适配、拆分或改写，不能直接解释为功能缺失。此前所谓“4 个历史提交未同步”只应视为待逐项审查的候选项。

## 默认自动交付（2026-10-22）

用户已持续授权本项目：每次功能新增、修改、修复、重构或撤销完成，经过实际 diff 审查并通过与风险相称的验证/测试后，代理自动完成提交、推送和交付收尾，不再停在“已修改，等你确认提交”，也不要求用户重复下令。本规则从本次规范修改起生效。

- **范围由需求决定。** 共享改动从 main 审查后交付 `origin/main`、`origin/TapModels`、`origin/tokensavy`；品牌专属改动只交付相应分支。只读分析、评审、提问不自动变成代码变更或交付任务。
- **当次限制优先。** 用户明确要求“仅本地”“先看效果”“不要提交”“只提交不要推送”“暂缓交付”或限定品牌/分支时遵从该限制，直到用户明确解除；默认授权不能覆盖这些要求。
- **交付条件不降低。** 先完成需求和必要旧路径清理、审核实际 diff、运行相关检查或复用输入仍一致的真实验证证据，再交付。失败先修复并补验；必需验证无法完成、需求未完成或存在未解决行为取舍时，说明具体阻塞，不把未验证代码推送。无实际变更时不制造空提交。
- **沿用现有交付流程。** 保持同一已核对官方基线上的单一定制提交，先备份，三方整合品牌文件树、更新累计说明、使用完整 refspec 和精确旧 SHA lease，优先原子推送。该持续授权包含执行既定结构所必需的历史替换；远端变化仍须审查保留，不能直接刷新 lease 覆盖。
- **保护并行工作。** 只交付本任务已完成且已验证的内容；工作区混有其他任务修改时在隔离候选中处理，不把全部暂存区或工作区一并推送，不移动其他任务正在使用的 HEAD。既有未完成任务不因本规则自动获得“已完成”状态。
- **交付后自动核验与收尾。** 核对实时远端 SHA、三个本地正式分支和工作区，清理本任务临时资源并保留必要恢复/验证证据。并行任务阻止本地安全对齐时，保留其现场，分别报告已完成的远端交付与未完成的本地收尾，写清后续条件；不要求用户为已授权的步骤再次确认。
- **不扩大外部操作范围。** 提交推送不授权 Run workflow、创建 Release/标签、发布镜像、生产部署、数据库迁移或数据删除。无需新增定时任务、Git hook 或自动推送脚本，由处理本次需求的代理在现有流程中执行。

## 1. 需求开始时判断，完成后复核

| 归属 | 判定依据 | 首次落地分支 | 默认交付范围（自动或显式提交、推送） |
| --- | --- | --- | --- |
| 共享能力 | 业务逻辑、安全修复、上游整合和经过审查的跨品牌能力 | main，验证后整合品牌预期树并分别归并 | origin/main、origin/TapModels、origin/tokensavy |
| KDAN 定制 | KDAN 专属品牌名称、资产、域名和商业政策 | main | origin/main |
| TapModels 定制 | TapModels 专属名称、域名、资产、商业政策、默认配置、部署、法律主体和繁体覆盖 | TapModels | origin/TapModels |
| Tokensavy 定制 | Tokensavy 专属名称、域名、资产、商业政策、默认配置、部署、法律主体和繁体覆盖 | tokensavy | origin/tokensavy |
| 混合 | 同一需求同时包含共享逻辑和品牌覆盖 | 先 main 审查，再对应品牌完整定制提交 | 本仓库 main → TapModels、tokensavy |

目录和关键词只能给出线索。例如 HomeView.vue 既可能是公共布局修改，也可能是品牌营销修改；语言包中的品牌名称不能使整个文件都变成品牌定制。审查实际 diff、用户需求和分支现有差异，不按文件整块归类。

开始实施时简述初步归属。完成需求后、首次提交前，输出简短交付说明：归属及理由、实际改动文件、提交分支、要传播到的品牌、明确远端 ref、验证结果。规则能确定时直接执行，不把这一步变成固定的批准问答。只有未确定的品牌政策或会改变行为的取舍才需用户决定。

用户明确限定某个分支时，以本次限定为准。默认自动交付和显式“提交、推送”都承接本次已确定的归属；共享内容默认从 `main` 传播到 `TapModels`、`tokensavy`，品牌定制不扩散到其他品牌。任何推送都不自动授权生产部署、数据库迁移或发布镜像。推送前核对 origin 的 URL 为本仓库及目标分支 CI 的实际副作用；超出本次授权时先完成可审查准备。

三个交付分支的 GitHub 发版 Workflow 仅保留 `workflow_dispatch`。版本发布和在线更新均使用本仓库对应分支/渠道，配置见 `scripts/release/channels.json`：`main/kdan`、`TapModels/tapmodels`、`tokensavy/tokensavy`。普通提交、推送、合并和标签推送不启动 Actions 发版，不创建 Release，也不提高版本号。代理或脚本不得在推送后自动调用 `gh workflow run` 或 dispatch API；只有用户明确要求发版时才执行。人工入口为本仓库 Actions → Manual versioned release → Run workflow，渠道和分支见 `deploy/AUTOMATIC_RELEASE.md`。同步上游保留此约束；工作流及相关守卫输入变化时运行 `test_auto_release_workflow.py`，否则复用有效检查，不因发生同步就重跑。

质量检查 Workflow 同样仅保留 `workflow_dispatch`，沿用用户要求的 Actions 只手动 Run；不得通过 push、PR、schedule 或其他自动事件启动。`test_auto_release_workflow.py` 对全部 Workflow 验证这一触发约束，业务验证继续在本机按改动风险执行。

## 2. 在正确分支形成提交

先核对 `git status`、当前分支、已有暂存、merge/rebase 状态、worktree 占用和目标远端。只暂存本次范围，不使用 `git add .` 混入其他任务。

共享需求的工作分支从 `main` 创建。不要在 TapModels 或 tokensavy 先实现共享逻辑再回搬；若工作目录在品牌分支，应从 main 创建隔离工作分支/worktree，把共享补丁应用并验证后再形成品牌覆盖。不得通过 reset、整文件覆盖或删除其他任务的修改来清场。

共享功能不能包含 TapModels 或 Tokensavy 专属名称、域名、法律主体或部署默认值；使用 `brand.go`、`brand.ts` 和运行时设置等品牌入口。混合需求先分清共享和品牌差异，main 先形成完整共享行为，各品牌再形成可审查的预期树；最终每个品牌只交付一笔完整定制提交。

## 3. 单一定制提交与品牌整合

### 单一定制提交（2026-10-22）

用户要求每次整理、同步和合并后，定制代码始终位于最新官方上游之上，避免本地提交与不断增长的上游历史混杂。本节取代此前“官方普通 merge + 多个本地功能提交”和“选择性来源更新归入对应功能提交”的最终交付方式；不改变功能范围、安全边界、来源审查或发版授权。

1. **固定输入。** 明确同步上游时获取 `upstream/main` 最新 SHA，核对来源为 Wei-Shaw；普通需求及纯历史重建沿用当前已核对的官方基线，不额外 fetch 来源。记录交付目标本地/远端旧 tip、官方基线和相关工作区状态。单分支任务不覆盖其他分支；分阶段交付记录各分支实际基线。只有用户要求全量定制对账时，才盘点全部工作树的暂存、未暂存、未跟踪与忽略源码，结合实际行为分类为待交付、已覆盖、已演进或已退役；不能仅凭“不同于main”断言遗漏。有效待交付内容完成审核/验证/归并后，旧现场才可备份清理。
2. **先得到正确的候选树。** 官方有新改动时，以旧官方基线、旧定制最终树、新官方树做三方整合；先按下文比较文本和语义冲突。可在隔离检出使用普通 merge 生成临时候选，但其历史不能直接发布。ranxi2001、New API、Codex Proxy RS、vm2api，以及明确授权的其他 Git 来源继续按当前需求审查、适配，全部归入唯一的定制树；不因整理历史扩大来源范围或整体合入未审核代码。无需同步新业务代码的纯历史整理保留原业务 blob/mode。
3. **完整累计说明。** 维护 [CUSTOMIZATION_RELEASE_NOTES.md](CUSTOMIZATION_RELEASE_NOTES.md)，按新官方基线到最终候选的实际 diff 更新新增功能、优化改进、Bug 修复、破坏性变更、升级指南、品牌差异、配置/默认值与来源。删除已被官方覆盖或已退役的本地功能描述；历史迁移存在不等于功能仍运行。提交正文包含完整可读累计说明及基线/来源记录，不能只有标题、上次增量或文件统计。每次正式 GitHub Release 都从该发布提交读取本文全文；版本区间增量只能补充，不能替代完整说明。新增、修改、优化或删除功能时，同次修订对应章节、配置/默认值、兼容性和升级指南，移除失效实现的有效能力描述，不只堆叠按日期日志。未更新完整说明的功能源码变化应在发布准备阶段阻止构建；完整性检查不能替代实际行为审阅。不自动发版。
4. **备份与压缩。** 在 Git 活动引用之外保留可验证的 bundle、旧 tip/树、来源作者和必要现场；保留正式标签、Release、附件及其他任务修改。从已验证候选树构建提交，唯一父提交为固定官方 SHA（可用 `git commit-tree <tree> -p <upstream> -F <完整正文>`）。不能 squash 上游自己的提交，不能将旧定制提交作为第二父节点。每个交付分支必须满足父提交恰为该 SHA，且 `git rev-list --count <upstream>..<candidate>` 等于 1。
5. **品牌传播按树进行。** 第一次转换先从真实旧 main/品牌共同基点整合；转为单提交结构后，共同 Git 祖先是官方基线，不能把它误当上一次共享版本。记录上次发布的 main/品牌树；有记录时用该 main 树作为明确三方基点应用共享变化，没有记录时先从来源归档恢复关系并核对品牌差异。得到每个品牌预期树后，各以同一官方 SHA 为唯一父节点形成一笔完整定制提交。不得把 main 的 KDAN 品牌覆盖灌入另两个品牌，不得把旧品牌分支 merge 回新历史。逐路径内容和 mode 核验候选树、完整品牌覆盖及共享实现。
6. **验证后交付。** 完整树等价可复用相关已通过验证；变化只补受影响检查。记录旧新 SHA、源 SHA、预期/最终树、测试和业务/测试增删。授权提交/推送即覆盖此结构所需的远端替换，非快进目标使用绑定已审核旧 SHA 的精确 `--force-with-lease`，完整 refspec，优先原子发布三品牌。远端新增提交须审查保留，不能刷新 lease 后覆盖。完成实时远端校验及本地正式分支收尾。

`deploy/sync-upstream.sh prepare/continue/status` 仅用于隔离候选的官方三方合并、冲突审查和验证；旧 merge 检查点的 `publish`/`run --approve-push` 已禁止，不能认证或直接发布重建后的最终提交。归并后使用已有 `tools/change_delivery.py` 验证器绑定实际候选，按本节直接发布最终 refs。旧 `deploy/sync.sh` 仍退役，不恢复固定六提交流程。

### 选择性来源更新归并（2026-10-17）

保留本标题供旧链接定位。其历史多功能提交规则已由上方 2026-10-22 单一定制提交规则取代；选择性来源的范围、署名、精确 lease、标签保护及不发版/不部署边界继续适用。不得从旧文档恢复多个功能提交或官方 merge 作为最终交付结构。

### 已验证改动的快速交付（2026-10-21）

“提交到之前相关提交里，然后推送”默认只交付本轮已完成的改动，不重新抓取来源、重做无变化功能审计或启动发版。它不是降低验证要求：将实现验证与历史整理分开，以内容和执行条件复用证据，避免把每次 SHA 变化都当成代码变化。

1. **实现阶段冻结证据。** 在现有 `.release/upstream-sync/<id>/` 中保存审查后的 `verification-plan.json` 和脚本实际执行生成的 `verification-receipt.json`；同步记录候选完整 tree、功能归属、三品牌旧 tip、已审查远端 SHA、预期品牌树和来源/作者。生成器先执行并审查输出，再明确暂存本任务候选；未暂存或未跟踪输入不能认证。计划必须覆盖所有相关源码、依赖、生成输入、工具链、构建参数及环境；不能只填几个改动文件。
2. **最小充分验证。** 按下方风险表选必要检查，不固定叠加 preflight、全量测试、vet、构建和 Workflow 守卫；关键回归失败先修复，已通过且输入未变的项续用，不因进入交付阶段升级全量。重型验证共用 Git common-dir 锁，可用 `--wait-seconds 300` 有界等待；超时保留检查点，不循环调用同一失败命令。只读 `validation-status` 不抢编译锁、不运行测试、不创建编译目录或写回执；它仍检查输入、命令和工具链。发现候选变更时停止本任务的过期进程组，绝不按进程名称杀其他任务。
3. **提交阶段先走快速路径。** 核对当前政策、候选、工具链和已审查远端基线，执行 `validation-status`。全部证据有效时，不重跑测试；完成单一定制归并、品牌树整合和完整 tree/mode 比较后，复核最终 ref 的 tree 等于已认证树。提交信息、父链、作者日期或 SHA 改变本身不使代码验证失效。两个品牌共享相同后端输入时复用后端结果，品牌实际差异另有自己的检查。
4. **发生变化只补受影响检查。** 计划项按完整输入范围、命令、依赖及工具链探针、环境指纹独立缓存；同一 receipt 的 `validate` 从首个未通过或已失效项继续，已通过且条件未变的项跳过。新代码、锁文件、构建参数或相关工具变化需要相应补验；远端新增提交先审查并纳入，不能只刷新 lease。没有可核验记录的旧口头测试结果，不手工伪造成成功 receipt。
5. **发布与收尾不省略。** 复用现有交付状态记录阶段完成情况和旧新 SHA 映射；已完成阶段输入未变则接续，不从来源同步或历史整理重新开始。推送仍按精确 lease、完整 refspec 和原子发布规则；随后核验实时远端、主目录正式分支、工作区与资源清理。验证 receipt 不替代语义审查、远端校验、推送授权或收尾记录。

工具复用 `tools/change_delivery.py`：`review/validate/validation-status` 不自动选择测试、不整理历史、不推送、不修改正式分支或生产环境；`delivery-run` 仅对明确传入的已授权命令提供跨 worktree 交付互斥，本身不生成 Git 或生产操作。选择性适配使用独立验证 receipt，不另建发布器：

```bash
python3 tools/change_delivery.py validate --plan .release/upstream-sync/<id>/verification-plan.json --receipt .release/upstream-sync/<id>/verification-receipt.json
python3 tools/change_delivery.py validation-status --plan .release/upstream-sync/<id>/verification-plan.json --receipt .release/upstream-sync/<id>/verification-receipt.json
```

计划结构如下（仅示范工作流检查；不能替代业务改动的实际测试计划）：

```json
{
  "version": 1,
  "checks": [{
    "id": "manual-workflow",
    "phase": "preflight",
    "cwd": ".",
    "inputs": [".github/workflows", "deploy"],
    "argv": ["/Users/luhonglin/.codex/tools/sync-upstream-validation/bin/python3", "-B", "-m", "unittest", "deploy.tests.test_auto_release_workflow"],
    "probes": [["/Users/luhonglin/.codex/tools/sync-upstream-validation/bin/python3", "-c", "import sys,yaml; print(sys.version, yaml.__version__)"]]
  }]
}
```

`inputs` 默认整个候选树；可按已审查的依赖范围缩小到受测包、相关依赖源码、共享夹具、生成输入、模块锁文件及生效的 workspace/构建输入，不能只指纹化改动文件。无法可靠界定时保留较宽指纹；指纹覆盖整个 backend 不等于必须运行全后端测试。`probes` 只放只读工具/依赖身份检查；可执行文件内容也计入指纹。`files` 声明忽略的已安装依赖清单（如 `frontend/node_modules/.modules.yaml`、实际存在的 pnpm 安装锁文件），缺失即失败；前端包含相关源码、锁文件、生成器和工具版本。`env_keys` 补充依赖的环境键，构建参数放在 `argv` 中；敏感值只保存摘要。检查按 `preflight` → `test` → `build` 排序，但没有必要检查的阶段可以省略，不为填满阶段添加命令。每项默认超时900秒，可按实际任务调整。

`validation-status` 只重新读取输入和执行只读身份探针；退出 0 才表示当前计划及候选均有有效证据，不能把探针写成测试或有副作用的命令。品牌树变化但部分结果可复用时，先 `validate` 绑定新候选并补缺失检查，再核对最终树。运行 Go 检查时，优先以选定 SDK 的 `go env GOCACHE` 核对既有缓存，显式传 `--go-cache <绝对路径>` 跨任务复用；工具前后实测 8 GiB 上限，超限不擅自删除共享缓存，报告收尾未完成。未指定时保持隔离缓存。`GOTMPDIR` 和完整日志始终任务隔离并清理，缓存存在不等于测试通过。多个缓存目录的合计上限仍须按收尾规范实测。

### 常规同步与串行交付（2026-10-22）

此节按用户的流程优化要求补充前述规则，不降低安全验证，也不把普通同步变成全仓重建。

- **先筛选，后固定范围。** 检查五个默认来源及本次明确指定来源的新增，复用已核查且输入未变的结论，深入本轮影响的调用链和有具体证据的既有缺口。官方无变化时不重演官方合并；无代码变化不制造空提交。需要新增产品、权限、留存策略或大规模重构的候选明确列为待决策，不拖住可独立交付的修复；已经批准或有现实安全风险的内容不能仅为赶时间跳过。New API 按整个网关收益评估，不以“以前没移植”排除候选；未纳入范围或本轮未核查的内容不推进 reviewed 水位。
- **实现可并行，交付要串行。** 所有本机任务在最终固定远端、整合品牌、验证、推送到本地对齐期间，共用 `delivery-run` 的 `change-delivery.lock`；不能只锁最后一次 push。使用 `python3 tools/change_delivery.py delivery-run --wait-seconds 300 --command <已审核命令及参数>` 包住该完整阶段，命令内部才读取最终 refs 和检查点。先解决产品取舍再进入交付，不持锁等待用户。这个协作锁不替代授权、精确 lease，也无法约束其他机器或仍使用旧流程的进程；旧任务不会自动加载新规则。
- **稳定候选只验一次。** 获得交付锁后复核远端漂移，审查并合入最新已发布内容，再固定组合候选和验证计划。范围确定后不继续追逐新来源更新；新发现的独立需求记录到下一轮。源树、依赖、生成输入或工具链变化只使相关检查失效，不因 SHA 改写、提交信息或交付阶段变化重跑。

### 最小充分验证（2026-10-23）

默认按实际差异与风险选择足以验证本次行为的最小检查集。执行前简述检查范围和理由；全量、race、真实数据库及 E2E 必须有具体触发原因，不作为固定套餐，也不为此新增审批轮次。先查明影响范围；仍无法可靠限定，或涉及广泛跨模块契约、共享依赖/构建机制改变且定向检查不足时，才升级全量。不能仅凭代码位于网关、鉴权、计费或调度目录就运行 `go test ./...`。

| 实际改动 | 默认验证与扩展条件 |
| --- | --- |
| 纯文档、注释、格式 | 差异及必要链接/格式检查；不跑业务测试或构建。实际改变生成输入或执行语义时按对应风险处理 |
| Skill、规范、流程脚本 | Skill 格式和代表性场景审阅；只有脚本行为变化才跑相关脚本测试，不为改文字重跑未变工具的整套测试 |
| 局部后端 | 问题回归及受影响调用链，不能只验证新函数；复用测试已经完成的编译，按实际静态分析缺口选择 vet |
| 前端逻辑 | 相关测试和必要类型检查；打包、入口、资源或构建配置有风险才构建。构建已包含相同 tsc 时不重复运行 |
| 权限、账务、调度、协议、恢复 | 必须覆盖受影响权限/账务不变量、入口、失败及恢复路径；跨层优先用服务/仓储/协议集成测试，完整用户流程受影响才补 E2E，不直接升级全仓 |
| 并发、锁、队列 | 在相关功能测试上补定向 race；没有并发影响时不默认运行 |
| SQL、Schema、迁移 | 受影响的真实数据库检查；没有持久化变化不启动数据库或缓存容器 |
| 仅修改测试 | 运行修改的测试；共享夹具、初始化、生成器变化扩展到使用者，不能机械限定为单个 unit 文件 |
| 仅提交、归并、推送 | 复用源码、依赖、生成输入、工具链、命令及环境仍匹配的真实证据；SHA、提交信息或无关说明变化不触发业务重测 |
| 品牌传播 | 共享行为验证一次，核对三方树及品牌覆盖；只有实际受影响的品牌逻辑、依赖、生成资源或构建参数才补对应检查，不因品牌名不同就重复全套构建 |

- **去重与续跑。** 不默认串联定向测试、全量测试、全量 vet 和全量 build。定向检查用于先定位独立风险；需要全量时不再重复其已覆盖检查。普通编译已被测试覆盖时不追加相同构建，但发布标签、embed、CGO、平台及资源打包差异不能视为已验证。失败后只修复并重跑失败或受影响项，不重置已通过且输入未变的步骤。
- **CI 边界。** Actions 仍只能人工 Run，不恢复 push/PR/schedule 自动触发，不擅自启动或等待远端 CI。工作流、渠道、交付配置或守卫输入变化时才运行对应 Workflow 检查；相关输入无变化则复用已核实的手动触发约束。纯后端不跑前端，反之亦然，除非实际跨层契约受影响。
- **一次整合。** 累计说明、来源和清单在候选稳定后统一更新，再绑定最终回执；只更改交付元数据时复用业务证据，不反复生成材料或重启验证。优先使用现有工具和可复用步骤，不每轮重新编写多套 prepare/deliver/finalize 脚本；缺少能力单独说明，不借流程优化扩建工具系统。
- **保留保护。** 未提交内容归属、必要权限与账务回归、语义冲突决策、最终树核验、可恢复备份、远端漂移审查、精确 lease、远端/本地对齐与本任务临时资源清理不能省略。缓存容量在昂贵检查前预检，保留限额内共享缓存，不因任务结束清空；没有使用的运行环境不启动、不遍历清理。不得把未运行的全量、数据库、浏览器或生产检查描述为已通过。

- **先检查验证前提。** 在启动昂贵测试前核对 SDK、依赖及已知测试生成文件；Ent `.entc` 等只用任务级、精确路径的排除配置，不扩大仓库忽略规则，更不能忽略真实未提交源码。未决定的业务冲突不得进入最终门禁。
- **减少中间材料。** 一份来源/取舍摘要、一份稳定验证计划和实际回执、一份交付映射即可；保留必要累计说明、来源署名与回滚备份。冻结的输入清单不混写后续提交 SHA/发布状态，避免无关元数据变化使证据失效；生成清单在最终树稳定后生成。默认读取摘要和失败片段，不反复读全量历史、测试原始输出或轮询未变状态。
- **异常收敛。** 外部进程造成漂移时，记录一次明确的漂移审查及缺失验证，不仅更新 lease；连续竞争时保留候选并报告阻塞，不无限重复构建/推送。耗时超过五分钟报告当前瓶颈和实际耗时；无冲突小改动 5–15 分钟、需完整回归 15–30 分钟只是优化目标，不是跳过检查的期限或保证。

速度目标：无代码/基线变化且已有完整证据时，将交付集中在归并、树比对、推送和收尾；2–5 分钟是优化目标，不是已经测得或对网络、冲突、品牌补验的耗时承诺。

### 协议适配的需求与验收证据（2026-10-24）

本节来自用户要求对 Cloud 全过程复盘并规范代理工作方式；约束开发与交付，不增加产品授权、启用、模型白名单或诊断开关。沿用前述最小充分验证和交付流程，不另建测试平台。

1. **先固定最终需求与真实入口。** 用当前用户要求确认授权复用、协议选择、模型权限、撤销范围和交付边界；不得自行把工程验证变成产品准入。先看目标客户端的真实序列化请求或脱敏样本，记录版本、配置和实际传输；最小上游探针不能替代客户端入口。只声明支持已核验的形态，不能靠删正常字段或放宽安全限制制造成功。
2. **按调用链比较既有实现。** 逐项追踪 HTTP JSON、SSE、客户端 WS、双向桥接，以及首轮、工具回传、完成后的新轮次、取消/断线、错误/重试和结算。对照原生/BPS 的实际调用点，不以同名 helper、代码量或文档描述证明复用。每项记录入口、复用点/必要差异、保护不变量和证据；已有正确能力不重复实现。
3. **先证明故障，再修完整路径。** 能本地复现的缺陷先加最小问题回归，再修改；至少检查相关入口到输出/账务边界，而非只测新函数。请求样本不能人为省掉客户端默认字段、工具目录或续接元数据。涉及继承/恢复时必须覆盖第二轮和传输切换；涉及流式写出时覆盖 Write/Flush 失败、取消和终态竞态。共享规则优先在原归属处修复。
4. **证据分级、不扩大结论。** 分别报告源码核对、本地函数/服务回归、真实客户端对本地网关/替身、真实上游、线上指定版本与账号验收。记录哪些层未执行。mock 上游成功不证明模型支持，CLI 启用 WS 不证明实际用了 WS，授权成功不证明客户端工具链可用，构建通过不证明线上恢复。禁止以“完整兼容/全部完成”等笼统结论掩盖未验收层。
5. **稳定后一次交付。** 完成本次已确认缺陷和撤销清理，冻结候选后按实际影响补验；复用输入未变的证据。新增独立能力或性能建议单列，不在验证期间无限扩围。最终交付分别列出已修复、已覆盖但未改、明确限制和线上待验收；真实调用、部署与迁移遵守已有授权，不把用户验收当作发现基本入口错误的第一道检查。

### 当前基线与验证范围（2026-10-17）

从 [v0.2.17 最终需求索引](requirements/final-v0.2.17-2026-10-17/README.md) 或其后续有效索引定位功能，再读取受影响组的最新实施、验收修订及实际调用链。索引的原始重建 SHA、TSV 和测试数字是历史快照，不能覆盖随后实现的调度、恢复或供应商需求。所有定制按上一节归并为一笔，不按历史重建记录恢复旧提交结构；旧 SHA 不在祖先链不等于功能缺失，先用来源归档和当前文件树核对，保留正式发布标签。

当前联动检查重点是：统一调度的资格、实际容量和优先级，跨重试/模式的整轮预算与 WS 后续轮，BPS 独立授权和图片阶段，供应商两级范围、归档与双边结算，以及 Ops/SLA 与账号健康的归因边界。规则归属仍在对应功能文档和生产实现，不另建同步专用业务规则表；具体调度与恢复以 [号池审计的最新实施章节](new-api-account-pool-scheduling-review-2026-10-17.md) 为准，供应商以 [统一平台验收](vendor-console/UNIFIED-PLATFORM-ACCEPTANCE.md) 为准。

以上是受影响时的检查线索，不是每轮执行清单。验证按“最小充分验证”选择：实际跨包生命周期变化覆盖相关组合；前端涉及打包风险才检查受影响主站/供应商入口，避免重复类型检查。手动 Workflow 守卫被触发时覆盖质量与发版全部工作流；真实数据库、竞态、浏览器、外部上游分别报告实际覆盖，不能用单测代替。输入未变的证据复用，不按来源、品牌或提交阶段重复全套。

其他任务占用或修改工作区时，可在已核对的提交基点创建隔离检出推进独立工作；只在尚未完成的代码确为本轮依赖时等待，不移动对方 HEAD、不暂存或发布其未完成内容。

### 同步冲突决策

同步的目标是以较少、清晰的实现满足当前最终需求。历史上采用过本地方案，不代表它永远优于上游；上游更新也不自动证明其方案正确。保护有效的需求和安全结果，不固守实现代码。

1. 固定本轮上游 SHA 和本地基点。审查三方 diff、相关调用链及需求依据，找出文本冲突和行为冲突，包括 Git 自动合并但可能改变权限、重试、计费、状态或配置含义的部分。文件重叠只是线索；跨文件改动也可能冲突。只深查本轮影响的功能，不每次重做全仓审计。

## 4. 明确推送目标并逐项验证

推送前 fetch origin 的所需目标分支，再基于最新远端核对快进关系、实际待推提交及工作流差异。依赖 fetch 结果的检查必须在 fetch 完成后执行。不 fetch 或发布旧 erwinlin 目标来完成当前交付。

```bash
git push origin refs/heads/main:refs/heads/main
git push origin refs/heads/TapModels:refs/heads/TapModels
git push origin refs/heads/tokensavy:refs/heads/tokensavy
```

只执行本次归属和授权所需的行。不使用裸 `git push`、`git push origin <短分支名>` 或依赖当前 HEAD 的目标推断。新 checkout 建议设置 `git config --local push.default nothing`，让遗漏 refspec 的推送直接报错。

完整交付可用 origin 的原子推送一次提交三个完整 refspec；逐项推送时记录成功和失败，部分失败保留成功结果，只修复并重试未完成目标。非快进拒绝后 fetch 并审查原因；已授权的单一定制交付目标可使用精确旧 SHA 的 lease，不以强推解决未知分叉。

使用 `git ls-remote --heads origin main TapModels tokensavy` 核对本次应交付分支的实际远端 SHA，分别对应各品牌的本地交付提交；三个品牌 SHA 无须相同。不能只读本地 remote-tracking ref 就声称远端成功。
