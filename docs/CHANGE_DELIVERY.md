# NewAPI 交付与资源收尾规范

## 维护目标

`NewAPI` 是本项目唯一维护、提交、推送和发版目标。原 `main`、`TapModels`、`tokensavy` 及早期重构引用只用于历史追溯、差异比较和行为核对，不接收本项目的同步提交，不创建同步标签，不向其发布镜像或附件。

上游同步和产品发版是两个独立动作：同步负责把经过审查的上游修复合并进 NewAPI；发版只在明确需要时由人工触发 GitHub Actions。推送代码不会自动发版、自动部署或迁移数据。

## 上游同步后的交付顺序

完整流程见[上游同步规范](UPSTREAM_SYNC.md)。每次同步批次按以下顺序收口：

1. 冻结 NewAPI 当前工作树、远端 `NewAPI` 和所有纳入范围的上游 SHA。
2. 审查实际差异，记录采用、已覆盖、排除和延期项；先解决行为冲突，再开始批量改代码。
3. 在隔离工作树中实现选定变更，保留当前 NewAPI 的架构、权限、品牌配置、部署和协议合同。
4. 运行受影响的后端、前端、部署和文档检查；协议、授权、账务、数据迁移和并发变化必须补对应场景证据。
5. 更新同步记录、交接资料和变更说明，核对未提交文件只属于本批次。
6. 按用户授权将本批次整理为一个累计 NewAPI 提交，并使用精确 lease 只推送 `refs/heads/NewAPI`。
7. 需要发布时另行人工触发 workflow，并记录发布输入、产物摘要和限制；没有发布授权时停在代码交付。

同步期间不得收取其他工作树未交付的改动，不得用 `reset --hard`、宽泛 `git clean` 或强推覆盖并发修改。远端 NewAPI 发生漂移时，重新审查并从最新目标重做候选，不能刷新 lease 强行覆盖。

## 提交、推送和发版

- 每个正式同步批次都以冻结的最新官方上游 `main` 为唯一父提交；NewAPI 的全部有效定制、重构代码和本批次修改整理成一个累计提交。不得继续把临时重构提交链作为正式同步父链。
- 一个同步批次在验证完成后只形成一个累计定制提交，提交正文引用完整 Release Note；提交与上游之间必须满足 `git rev-list --count <upstream>..<candidate> == 1`。
- 推送使用完整 refspec 和精确旧 SHA lease，目标固定为 `holeenlu/sub2api` 的 `refs/heads/NewAPI`。
- GitHub Actions 只允许人工 `workflow_dispatch`。手动发版使用当前工作流和明确版本输入；推送 NewAPI 不触发自动发布，不修改旧维护分支的标签、Release 或 Latest。
- 提交或推送不代表生产部署、数据库迁移、数据恢复、真实上游验收或用户人工验收完成；这些动作必须有单独授权和证据。

## 验证和证据

验证按实际影响选择，输入、依赖、源码和工具链未变化时可以复用有效证据；不能因为提交 SHA 变化就重复无关的全量测试，也不能把未运行的检查写成通过。

| 变化 | 最小充分检查 |
| --- | --- |
| 文档、规则、来源记录 | 链接、路径、JSON和差异检查 |
| 局部 Go 或 TypeScript | 受影响包测试、类型/静态检查和真实消费者检查 |
| 协议、授权、账务、调度、并发 | 成功、拒绝、取消、恢复、归属、幂等和并发边界 |
| 数据库、迁移、配置 | 隔离数据库/Redis上的真实启动、迁移、回滚和对账 |
| Docker、部署和构建 | 对应角色构建、启动、健康、持久化和升级检查 |
| 前端页面 | 前端 owner 执行对应测试、构建和实际浏览器操作；后端不能代报页面通过 |

本地 Docker 验收使用独立项目、卷、网络和测试凭据；不得复制生产凭据或生产数据。协议和真实上游条件不足时记录 `blocked` 或 `not_run`，不使用替身结果替代真实验收。

## 回滚和收尾

同步前保留当前 NewAPI SHA、上游冻结 SHA、候选工作树和可恢复 bundle。推送前验证远端旧 SHA；失败时优先恢复本批次候选和工作树，不修改其他分支。

收尾只删除本批次拥有的临时工作树、日志、构建二进制、测试卷、网络和不再使用的镜像；保留必要的同步记录、短验证回执、当前开发源码、有效 Docker 联调资源和共享缓存。不得全机清理缓存或删除其他任务资源。
