# 需求归属与提交、推送规范

适用于新增功能、修复、重构、合并需求及其交付。当前采用 `main` 作为 KDAN 品牌主分支、`TapModels` / `tokensavy` 品牌派生和 `upstream-base` 官方基线的结构。目标是先判断改动归属，再选择提交位置和发布目标；当前检出的分支只是工作现场，不能作为归属依据。

## 当前分支结构

共享新增、修改、删除、重构和官方上游整合先在 `main` 完成。`main` 即 KDAN 品牌分支；`TapModels`、`tokensavy` 通常接收 `main` 的普通 merge，再单独保留品牌覆盖。三个选择性来源更新适用下文“选择性来源更新归并”的明确例外。品牌专属需求只在对应分支完成。远端不再维护独立 `KDAN` 或公共分支；`upstream-base` 只保存官方上游引用，不承载本地品牌代码。完整结构见 [分支结构与品牌交付模型](BRANCH_STRUCTURE.md)。

自 2026-10-03 起，代码推送仅限本仓库 `holeenlu/sub2api` 的 `origin/main`、`origin/TapModels`、`origin/tokensavy`；不再推送 `erwinlin/main` 或其他仓库。推送目的地不能由跟踪关系推断，一律写全源、目标 ref。旧文档、历史整合记录、已保存检查点中的旧目标不能覆盖现行规则。

`git cherry` 的 `+` 表示未找到等价补丁，可能来自品牌适配、拆分或改写，不能直接解释为功能缺失。此前所谓“4 个历史提交未同步”只应视为待逐项审查的候选项。

## 1. 需求开始时判断，完成后复核

| 归属 | 判定依据 | 首次落地分支 | “提交、推送”的默认交付范围 |
| --- | --- | --- | --- |
| 共享能力 | 业务逻辑、安全修复、上游整合和经过审查的跨品牌能力 | main，验证后普通 merge 到品牌分支 | origin/main、origin/TapModels、origin/tokensavy |
| KDAN 定制 | KDAN 专属品牌名称、资产、域名和商业政策 | main | origin/main |
| TapModels 定制 | TapModels 专属名称、域名、资产、商业政策、默认配置、部署、法律主体和繁体覆盖 | TapModels | origin/TapModels |
| Tokensavy 定制 | Tokensavy 专属名称、域名、资产、商业政策、默认配置、部署、法律主体和繁体覆盖 | tokensavy | origin/tokensavy |
| 混合 | 同一需求同时包含共享逻辑和品牌覆盖 | 先 main，再对应品牌提交 | 本仓库 main → TapModels、tokensavy |

目录和关键词只能给出线索。例如 HomeView.vue 既可能是公共布局修改，也可能是品牌营销修改；语言包中的品牌名称不能使整个文件都变成品牌定制。审查实际 diff、用户需求和分支现有差异，不按文件整块归类。

开始实施时简述初步归属。完成需求后、首次提交前，输出简短交付说明：归属及理由、实际改动文件、提交分支、要传播到的品牌、明确远端 ref、验证结果。规则能确定时直接执行，不把这一步变成固定的批准问答。只有未确定的品牌政策或会改变行为的取舍才需用户决定。

用户明确限定某个分支时，以本次限定为准。“提交、推送”承接本次已确定的归属；共享内容默认从 `main` 传播到 `TapModels`、`tokensavy`，品牌定制不扩散到其他品牌。任何推送都不自动授权生产部署、数据库迁移或发布镜像。推送前核对 origin 的 URL 为本仓库及目标分支 CI 的实际副作用；超出本次授权时先完成可审查准备。

三个交付分支的 GitHub 发版 Workflow 仅保留 `workflow_dispatch`。版本发布和在线更新均使用本仓库对应分支/渠道，配置见 `scripts/release/channels.json`：`main/kdan`、`TapModels/tapmodels`、`tokensavy/tokensavy`。普通提交、推送、合并和标签推送不启动 Actions 发版，不创建 Release，也不提高版本号。代理或脚本不得在推送后自动调用 `gh workflow run` 或 dispatch API；只有用户明确要求发版时才执行。人工入口为本仓库 Actions → Manual versioned release → Run workflow，渠道和分支见 `deploy/AUTOMATIC_RELEASE.md`。同步上游时保留此手动触发约束，并运行 `test_auto_release_workflow.py` 防止自动触发器回流。

质量检查 Workflow 同样仅保留 `workflow_dispatch`，沿用用户要求的 Actions 只手动 Run；不得通过 push、PR、schedule 或其他自动事件启动。`test_auto_release_workflow.py` 对全部 Workflow 验证这一触发约束，业务验证继续在本机按改动风险执行。

## 2. 在正确分支形成提交

先核对 `git status`、当前分支、已有暂存、merge/rebase 状态、worktree 占用和目标远端。只暂存本次范围，不使用 `git add .` 混入其他任务。

共享需求的工作分支从 `main` 创建。不要在 TapModels 或 tokensavy 先实现共享逻辑再回搬；若工作目录在品牌分支，应从 main 创建隔离工作分支/worktree，把共享补丁应用并验证后再形成品牌覆盖。不得通过 reset、整文件覆盖或删除其他任务的修改来清场。

共享功能不能包含 TapModels 或 Tokensavy 专属名称、域名、法律主体或部署默认值；使用 `brand.go`、`brand.ts` 和运行时设置等品牌入口。混合需求拆提交，main 先形成完整共享行为，各品牌再形成可审查的品牌覆盖。

## 3. main 改动传播到品牌分支

默认采用普通 merge 保留来源提交 SHA；发生下述已授权的选择性来源归并时，采用对应的品牌重新接续流程。选择合并来源前必须审查拟合入的完整差异，不能为了一个新功能无意带入未知历史差异。

- 最佳路径：从 main 创建工作分支，完成共享行为和验证后普通 merge 回 main，再普通 merge 到 TapModels、tokensavy。品牌分支只新增品牌覆盖，不复制共享实现。
- 官方更新先普通 merge 到 `main`；main 验证完成后再普通 merge 到 TapModels、tokensavy。`upstream-base` 只作为来源基线，不直接作为品牌发布分支。
- 历史有大量分叉、此次仅需传播一个已审核需求：先明确报告有限范围移植的理由，可用 `cherry-pick -x <来源 SHA>` 传播该提交或依赖完整的提交序列。这会产生不同 SHA，交付表必须记录来源关系，不称作全历史合并。
- 品牌已存在等价改动：核对代码、品牌适配和行为证据后跳过重复应用，记录对应 SHA。没有新的品牌提交时无需空推送。

无需因历史分叉自动停止；继续核实本次可独立交付的变化。待审历史项另行列明，不能仅凭祖先检查、提交计数或 patch-id 判断缺失。品牌适配造成的补丁差异必须通过实际 diff 和相关测试解释。

上游同步仍使用 `deploy/sync-upstream.sh` 的普通 merge 流程；它同步 upstream，不是 main 向 TapModels 传播的替代入口。不要调用旧 `deploy/sync.sh` 的线性 rebase、固定六提交或 force-push 工作流。

### 选择性来源更新归并（2026-10-17）

用户明确要求：`ranxi2001/sub2api`、`QuantumNous/new-api`、`MACOS-DO/sub4api` 同步吸收的更新，归入本地原有对应功能提交后再推送。此规则持续适用于后续已授权的同步、提交、推送任务，覆盖这些更新默认追加提交和禁止重写的旧约定；Wei-Shaw 官方提交仍普通 merge、保留原 SHA。技能维护本身不启动同步或远端推送。

1. **先映射归属。** 按实际功能和依赖定位原有本地提交，例如 BPS、账号调度、Responses 恢复、协议兼容、诊断或 Ops；一个来源可拆入多个既有主题，多个来源的等价修复只实现一次。现行主题和来源归档提供线索，不能固定旧 SHA 或仅凭标题判断。确无对应主题的新能力才新增一个必要的功能提交，并说明理由。
2. **验证最终结果再整理历史。** 固定三分支及远端旧 tip，保留可恢复的提交备份、未提交现场和来源记录；在隔离检出中将本轮已审核改动归入对应提交，维护原作者和来源署名。允许必要的后继本地提交重接父链，保留其全部无关内容。不得线性重放或改写 Wei-Shaw 原始提交，不把本次授权扩展为全仓历史清理。
3. **核对等价文件树。** 用“原最终代码＋本轮已验证改动”的候选树比对归并后完整路径、内容和 mode；记录主题旧新 SHA 映射及外部来源 SHA。临时 fixup/增量提交不作为最终交付历史。树和相关工具链未变的验证可复用；树不同则重新审查并补受影响检查。
4. **品牌接续。** main 历史未变时仍普通 merge。main 已归并时，先根据旧 main 与各品牌的真实共同基点做三方合并，得到包含本轮共享结果和完整品牌改动的预期树，再将原品牌覆盖提交接续到新 main 并核对树；不把旧品牌分支直接 merge 回来而重新引入已替换的共享提交。保留各品牌独立改动、作者及来源，不用整文件覆盖解决冲突；未决定的产品取舍按冲突决策流程处理。
5. **推送已批准的归并结果。** 本规则连同本轮同步/推送指令，已授权上述有限范围的历史归并及所需远端替换，无需逐次重复询问。只对实际非快进的目标使用精确 `--force-with-lease=refs/heads/<分支>:<已审查远端旧SHA>`，同时写完整 refspec，优先三分支原子推送；快进目标用正常推送。远端变化时重新核查并纳入新增内容，不能仅刷新 lease 后覆盖，也不能用无条件 `--force`。
6. **保留交付边界。** 正式版本标签、Release 与附件保持原指向；其他任务的未完成内容不混入，正在使用的 worktree 不被强行切换。旧检查点的 tree、review、publish 记录不能认证归并后的新提交，也不修改其指纹绕过保护。最终逐项核验三个远端 SHA；此规则不授权发版、部署或数据库迁移。

### 当前基线与验证范围（2026-10-17）

从 [v0.2.17 最终需求索引](requirements/final-v0.2.17-2026-10-17/README.md) 或其后续有效索引定位功能，再读取受影响组的最新实施、验收修订及实际调用链。索引的原始重建 SHA、TSV 和测试数字是历史快照，不能覆盖随后实现的调度、恢复或供应商需求。选择性来源归并按上一节执行，不据历史重建记录扩大改写范围；旧 SHA 不在祖先链不等于功能缺失，先用来源归档和当前文件树核对，保留正式发布标签。

当前联动检查重点是：统一调度的资格、实际容量和优先级，跨重试/模式的整轮预算与 WS 后续轮，BPS 独立授权和图片阶段，供应商两级范围、归档与双边结算，以及 Ops/SLA 与账号健康的归因边界。规则归属仍在对应功能文档和生产实现，不另建同步专用业务规则表；具体调度与恢复以 [号池审计的最新实施章节](new-api-account-pool-scheduling-review-2026-10-17.md) 为准，供应商以 [统一平台验收](vendor-console/UNIFIED-PLATFORM-ACCEPTANCE.md) 为准。

验证以最终组合为单位：共享预算、调度、鉴权或恢复生命周期变更执行跨包回归；影响共享前端时检查主站及既有供应商门户构建。相同输入、命令和工具链的通过结果可复用，不按来源或品牌重复全套。手动 Workflow 检查覆盖质量与发版全部工作流；真实数据库、竞态、浏览器、外部上游分别报告实际覆盖，不能用单测代替。纯流程/技能维护执行脚本及场景验证，不触发业务全量构建。

其他任务占用或修改工作区时，可在已核对的提交基点创建隔离检出推进独立工作；只在尚未完成的代码确为本轮依赖时等待，不移动对方 HEAD、不暂存或发布其未完成内容。

### 同步冲突决策

同步的目标是以较少、清晰的实现满足当前最终需求。历史上采用过本地方案，不代表它永远优于上游；上游更新也不自动证明其方案正确。保护有效的需求和安全结果，不固守实现代码。

1. 固定本轮上游 SHA 和本地基点。审查三方 diff、相关调用链及需求依据，找出文本冲突和行为冲突，包括 Git 自动合并但可能改变权限、重试、计费、状态或配置含义的部分。文件重叠只是线索；跨文件改动也可能冲突。只深查本轮影响的功能，不每次重做全仓审计。
2. 在解决需要取舍的语义冲突前，将对照写入本轮 `upstream-changes.md` 并展示给用户。按功能/流程分组，列出文件及提交证据、上游和本地各自的触发条件、正常/失败路径、数据和配置变化、本地需求的来源与当前有效性。未知项明确标为待核实。
3. 每组比较采用上游、保留本地、融合两侧的收益与代价，明确会失去什么、是否涉及兼容/迁移及维护成本；不适用的选项说明原因。给出一个推荐方案及依据。两侧都不理想时可提出更简单的替代方案。融合必须说明规则归属、优先级及失败路径，不以双实现、永久兼容层或更多开关掩盖冲突。
4. 上游已完整覆盖本地需求时，推荐采用上游并清理被替代路径；本地方案仍更符合当前需求时，可以推荐保留并说明差距。品牌、安全、数据保护等明确约束仍须满足，但不要求保留旧实现；若推荐方案改变这些约束或存在未决定的产品取舍，先取得用户决定，再做依赖该决定的修改。纯机械冲突和已经明确决定的等价行为直接处理，不重复问答。
5. Git 自动合并结果也须在验证、提交和推送前审阅。脚本的 `--reviewed` 记录执行者完成审阅，不替代用户对需求变更的决定，也不授权推送。每个品牌复核实际差异和品牌覆盖；相同公共逻辑复用主分支分析，品牌有新行为差异时才单独比较。
6. 最终记录实际采用方案、删除或替换的本地路径、保留原因和独立风险的验证结果。旧决定仅在输入和需求仍相同时复用；代码或需求改变后重新评估。验证通过不等于需求成立，祖先关系不等于功能等价。

详细对照只针对有实际取舍的冲突；无冲突时给出核查范围和结论即可。依赖同一语义决定的多个文件可以合并说明，互相独立的产品选择不能捆绑成一次“全部保留”。

### New API 更新吸收

2026-10-13 用户明确：New API 更新应按其对整个网关的价值评估和吸收，不局限于此前已经整合的内容。该规则适用于后续研究、更新筛选、实施与验收；Wei-Shaw 仍为官方上游基线，New API 作为可吸收改进的参考来源。

1. **覆盖整个网关。** 比较模型与协议适配、HTTP/SSE/WebSocket、请求解析与大小限制、上下文与工具传递、连接与资源管理、并发与调度、错误分类与传播、重试与故障转移、鉴权与安全、用量与计费一致性、监控诊断、依赖维护等实际收益。不得只以能否解决当前某条错误判断价值。
2. **同时检查增量和既有缺口。** 每轮固定 New API 源码 SHA、本地基点与先前核查范围。新增提交用于定位变化，已有版本中未充分评估或尚未吸收的相关能力同样纳入；不因未曾移植该模块、不同框架或不在最新增量中而直接排除。按具体变化追踪受影响的调用链，无需无依据地每次重审全仓。
3. **判断实际行为是否覆盖。** 对本地同名功能检查入口、正常和异常分支、重试与资源生命周期及测试证据。某入口已返回 413、某函数能分类错误，不等于整条链路已覆盖。依赖升级应核对实际解析版本、生产调用路径和最终版本行为；版本已覆盖时不重复修改，不把声明版本当成线上部署证据。
4. **按收益实施吸收。** 将候选分为“应吸收”“部分覆盖需补齐”“已等效覆盖”“当前不适用”并给出证据。对符合现行需求、安全边界且收益明确的改进，在本次任务既有授权范围内直接实施、验证并纳入交付，不逐项重复询问是否吸收。部分覆盖时修复缺口；已有实现不能作为永久保留理由，更完整、简单的方案应优先采用并清理被替代路径。
5. **落到本地单一实现。** 优先融入现有网关入口、协议适配、调度、错误处理、计费与日志机制，避免平行网关或重复规则。New API 的参考吸收按语义适配和可追溯来源记录实施，不将跨项目整分支 Git merge 视为默认手段；共享成果按“选择性来源更新归并”落入 main 对应功能提交，再完成品牌接续与交付。
6. **以效果验收。** 记录来源提交、解决的问题、本地受影响入口、采用方式、预期收益及测试结果。针对独立风险验证错误根因、状态码、上游尝试与重试边界、计费一致性、流式/WS 恢复、资源释放和敏感信息保护；未验证的性能或稳定性收益不得写成已实现。

该原则支持网关能力持续提升，不能用于恢复明确退役的能力或绕过现行品牌、安全和产品语义约束。确有未决定的语义冲突，仍按“同步冲突决策”处理；提交、推送、发版、生产部署和迁移继续适用各自的既有授权规则。

## 4. 明确推送目标并逐项验证

推送前 fetch origin 的所需目标分支，再基于最新远端核对快进关系、实际待推提交及工作流差异。依赖 fetch 结果的检查必须在 fetch 完成后执行。不 fetch 或发布旧 erwinlin 目标来完成当前交付。

```bash
git push origin refs/heads/main:refs/heads/main
git push origin refs/heads/TapModels:refs/heads/TapModels
git push origin refs/heads/tokensavy:refs/heads/tokensavy
```

只执行本次归属和授权所需的行。不使用裸 `git push`、`git push origin <短分支名>` 或依赖当前 HEAD 的目标推断。新 checkout 建议设置 `git config --local push.default nothing`，让遗漏 refspec 的推送直接报错。

完整交付可用 origin 的原子推送一次提交三个完整 refspec；逐项推送时记录成功和失败，部分失败保留成功结果，只修复并重试未完成目标。非快进拒绝后 fetch 并审查原因；仅上述已授权归并目标可使用精确旧 SHA 的 lease，不以强推解决未知分叉。

使用 `git ls-remote --heads origin main TapModels tokensavy` 核对本次应交付分支的实际远端 SHA，分别对应各品牌的本地交付提交；三个品牌 SHA 无须相同。不能只读本地 remote-tracking ref 就声称远端成功。

### 本地正式分支收尾

此要求适用于所有提交、推送任务，包括普通修复、功能修改、清理和归并，不限于上游同步。隔离仓库或 worktree 推送完成后，还必须检查主目录 `/Users/luhonglin/Git/sub2api` 的 `main`、`TapModels`、`tokensavy`。归并重写 SHA 后，只更新远端跟踪引用会使正式本地分支停留在旧历史，Sourcetree 因而同时显示领先、落后。

1. 以本轮发布记录核对旧本地 tip、已审核的新 tip 和实时远端 SHA；不能只凭 ahead/behind、提交标题或 `git cherry` 判断本地内容可丢弃。确认不存在独有未交付提交，并检查未提交修改、暂存、未完成 Git 操作和 worktree 占用。
2. 将原 tip 和受影响现场备份到 Git 引用以外。主目录干净且没有其他任务占用时，使用绑定旧 SHA 的引用更新对齐正式分支；当前检出分支还须同步工作文件和索引，不能只移动 ref。不得覆盖其他任务的修改、移动对方正在使用的分支，或把已替换的旧历史 merge 回来消除分叉。
3. 更新后重新读取实时远端，确认本轮目标与审核结果一致；逐一核对三个本地分支与各自远端跟踪分支的 `git rev-list --left-right --count` 均为 `0 0`，并检查主目录工作区。若某分支不属于本轮目标但存在分叉，先核实其交付记录和独有内容，不能顺手覆盖；明确报告该分支未对齐。
4. 并发任务、未提交修改、独有提交或远端漂移使安全对齐无法完成时，保留现场，分别报告“远端已发布”与“本地收尾未完成”的分支及原因；不能只凭远端验证成功就宣称全部交付完成。清理引用时也须复核此状态，不能将未交付或未完成的内容当作无用历史删除。

## 5. 验证、修正与完成条件

按实际行为风险验证，不仅看 Git 是否无冲突。首页类改动检查组件行为、多语键完整性、类型及浏览器布局；main 改动传播到 TapModels、tokensavy 后检查各品牌标识和相关回归。相同产物无需无理由重复全套测试。

误提交到 TapModels 但尚未推送时，先保留提交和用户现场，在正确的 main 基线上重建本次提交。已经推送时保留历史，通过可追溯移植或审核后的合并纠正；若要撤销远端提交，应单独确认并优先 revert，不擅自 reset/force-push。

用户明确要求 rebase/压缩重新提交时，可以在已明确的提交范围内执行：先备份原 tip 和包含未提交内容的完整检查点，再重排或合并提交，核对重写前后的文件树。该指令覆盖默认保留历史规则，但不等于允许覆盖所有远端或重写其他任务提交。三个选择性来源的持续授权见上文，其余重写已发布历史的远端更新仍须明确覆盖授权并使用精确旧 SHA 的 force-with-lease；未获授权时保留现有远端，说明剩余交付范围。

完成报告包含 main、TapModels、tokensavy 本次应交付的源分支、origin 远端 ref、实际 SHA、合并或等价移植关系、验证及失败项，并列出主目录三个本地正式分支 SHA、领先/落后计数及工作区状态。本次应交付的所有目标分支已验证后，才称“品牌同步完成”；本地收尾仍未完成时必须单独说明，不能宣称整体交付完成。
