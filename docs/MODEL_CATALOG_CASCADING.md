# 模型目录能力透传与级联

sub2api 通过 API Key 接入另一个 sub2api 时，普通 `GET /v1/models` 同时提供模型名称和已知的共同能力。该行为属于共享后端，适用于所有品牌；无新增开关或数据库迁移。

## 接口格式

保持 `{"object":"list","data":[...]}` 以及原有 `id`、`object`、`owned_by` 等字段，按已知信息增加：

- `model_kind`
- `reasoning`、`supported_reasoning_levels`、`default_reasoning_level`
- `input_modalities`、`output_modalities`
- `context_window`、`max_context_window`、`max_output_tokens`

未知值省略；明确不支持推理时输出 `reasoning:false`。普通模型名单、排序和分组权限保持原规则，图片模型不会因缺少对话上下文字段被删除。`GET /v1/models/:model` 返回相同能力字段。旧客户端可以继续仅解析原字段。

只从该 Key 对应分组的可供应账号中，读取经过凭证范围及有效期校验的模型快照。别名按实际上游映射取证据，返回仍使用公开名称。多个供应账号共同承载同一模型时，推理档位和输入/输出类型取交集，上下文和输出上限取共同可保证的较小值；缺少某字段时不借用其他账号补造该字段。目录查询不触发上游网络访问，不输出账号ID、凭证、上游模型名称、供应商指令或内部快照。

## 部署与验证

1. 升级提供 API Key 的上游 sub2api，先确认模型目录同步获得真实能力。
2. 使用发给下游的同一把 Key 请求上游 `/v1/models`，核对模型权限及能力字段。
3. 下游在账号编辑中同步上游模型，或在模型目录管理页执行同步。已有 sub2api 解析器能识别上述字段，无需改用 Codex 专用接口。
4. 检查下游账号对应模型的缺失能力标记清空，再下载 `/keys` 中的 Codex 目录。

实际推理能力仍以供应商服务为准；目录信息不等于真实推理测试。仅提交代码不会更新生产镜像、执行目录同步或改变线上账号设置。

## 其他供应商

不限模型名称或 GPT 系列。OpenAI 兼容供应商若在模型列表返回这些字段，现有解析器可以读取；已有解析器也支持部分供应商的原生字段，例如 Claude 的输入上限/effort 信息和 Gemini 的 token limit 字段。成功同步到完整信息后，sub2api 可用同一格式继续向下游公布。

只返回名称的供应商仍可能缺少能力，具体取决于现有注册表补充能否匹配其供应商和模型；不会从另一个 OAuth 账号复制能力，也不新增第三方端点探测。不同第三方网关不一定识别扩展字段，需要它们自己的解析支持。

本实现不增加额外 Codex 目录读取，不硬编码上下文/推理档位，也不放宽混池 Codex 目录原有的完整性检查。
