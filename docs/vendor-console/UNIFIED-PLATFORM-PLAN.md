# 统一供应商平台实施方案（2026-10-17）

适用：KDAN / TapModels / Tokensavy 共享业务。本文取代旧方案中普通用户附加供应商身份、邮箱邀请开户、供应商审计/安全独立菜单及手填合同版本的决定。状态：先完成方案，再实现后端与正式 Vue；本地验证结果见 [验收记录](UNIFIED-PLATFORM-ACCEPTANCE.md)，尚未生产部署。

## 一、产品与服务边界

采用一个后端、一个 PostgreSQL、一个 Redis、两套域名入口。客户站承载终端客户、消费 API Key、用户运营与必要系统设置；供应商站统一承载供给管理后台、一级控制台、二级控制台。复用现有登录、会话、MFA、原生账号/代理、分组和网关调度，不复制数据库、计费网关或后台任务。

独立域名通过反向代理转发同一应用的供应商前端及允许的 API。供应商站复用原 Bearer Token 登录，以独立 Origin 隔离浏览器存储；不在域名间转发登录 Token，不配置共享父域 Cookie 或通配 CORS。后端仍按实时角色、资源归属、上下级和状态授权，域名及前端菜单不构成权限。客户站与供应商站的登录重定向均有固定白名单。部署和生产数据迁移另行执行，本次只实现和本地验证。

| 身份 | 可见与操作 | 财务范围 |
| --- | --- | --- |
| 超级管理员 super_admin | 统一供应商站后台；全部供应商账号/代理；开户、策略与平台治理 | 平台→一级应付及经授权的链路核验 |
| 一级 vendor_level1 | 管理自己资源和直属二级身份；直属二级资源仅列表、详情、报表只读 | 平台→自己应收；自己→直属二级应付，分别定价 |
| 二级 vendor_level2 | 只管理自己的账号、代理；不能创建下级 | 上级→自己应收；不能读取上级采购价或其他供应商 |
| admin / user | 原客户运营后台 / 客户站，不拥有供应商身份 | 原消费侧账单、余额、订阅 |

超级管理员创建一级；创建二级时必须明确选择有效一级作为上级。一级开户只能产生直属二级，服务端强制其父级，不能提交其他 parent_id。层级、父级和资源直接所有者创建后不可随编辑迁移。账号归档仍保留列表、身份占用和历史，不改为物理删除。

账号与代理的上级视图默认展示完整工作台：超级管理员展示全部供应商资源，一级展示全部直属二级资源；供应商选择改为可选过滤。列表常驻归属供应商名称和ID，可点击缩小范围。详情与用量使用实际行归属，汇总状态、分页和统计由后端同一范围返回；一级始终只读，超管选择归属后使用既有管理权限。

## 二、页面与开户

供应商侧栏移除“操作审计”“账号安全”。后台审计仍记录；头像中的账号设置仍提供个人资料、修改密码及项目既有认证安全功能。保留四语与浅色/深色/跟随系统。独立供应商站按角色显示后台或控制台，不展示假角色切换器。

新增供应商删除“登录账户来源”和绑定普通用户入口。输入邮箱、密码、用户名、供应商名称、级别、必要的上级及供给范围。密码使用原项目校验与哈希，不返回、不进入审计或日志；用户、供应商、关系和初始策略须原子创建，失败不能遗留半开通用户。既有同邮箱不能静默改角色。

新建默认：账号上限 1000、代理上限 1000、每个上游账号默认并发 15、默认优先级 1、统计倍率 1。编辑已有供应商保留原值；改默认不回写已有账号。一级上限计算自有与直属二级的实际资源总量，二级同时受自身和父级总量限制；归档账号仍计入名额，不删除历史以释放名额。资源列表及汇总按直接所有者计数；一级额度另外展示含直属二级的总占用，避免重复加总。二级授权平台、分组、直连能力须为一级有效授权子集。暂停上级不能使下级继续登录、写入或新调度；恢复不能覆盖子级自己的停用、账号暂停或归档。

供应商添加代理复用管理后台的字段和交互顺序：名称、协议、主机、端口、用户名、密码，以及原后台支持的可选字段/快捷添加。字段是否存在以当前 `/admin/proxies` 实际实现为准；供应商专有生命周期信息放编辑或高级信息，避免把新增界面做成另一套表单。下级只读查看不返回代理密码、令牌或其他凭证。

## 三、价格、版本和账务

当前“合同系数（CNY/USD）”是约定采购单价：每 1 USD 统计用量折算多少 CNY；不是市场汇率，也不是客户充值/消费倍率。现有结算再按约定 CNY/USDT 汇率折为 USDT。界面改为明确单位的“结算单价（CNY / 统计 USD）”，分组覆盖价优先于默认价。例：统计用量 100 USD × 单价 1.8 CNY/USD ÷ 约定汇率 6.7 CNY/USDT，按现有账单舍入规则结算；仅为公式说明，非运营报价。

合同版本是价格规则的修订号，由服务器在价格变化时增加；创建从 1 开始，用户不能手填。账单保存价格、版本、汇率来源、时区和用量快照，修改新合同不能改变已确认历史账单。明确区分原始模型成本、账号统计成本、客户实际扣费、采购结算金额。

平台→一级、一级→二级是两条独立结算边。二级供给产生的一条真实用量可分配到两条边各一次，不能在同一条边重复结算；一级自有供给仅有平台→一级一条边。每条边各有价格/版本/账单/付款/冲正，不用父级价格推导子级价格。一级给二级出账时由服务器读取该二级的当前合同；不能在预览请求中伪造价目或版本。超级管理员原有手工历史分段、覆盖价及依据录入继续保留。本轮未新增按生效日期自动选择历史合同的价格档案。一级毛差由同批可比用量的两条边计算，不能把全部客户收入当供应商利润。

用量记录保留请求当时的直接 owner、root/parent 关系和合同归属，不以当前账号状态或可编辑归属重算历史。客户消费仍归原 API Key 用户、消费分组和订阅；供应商采购归供给账号及结算边。禁止将供应商本人用户 ID 替换消费请求的 user_id。归档、停用和改名均不得丢失历史。

## 四、调度、权限和默认值

供应商建立的账号使用原 accounts / account_groups / proxies，校验平台匹配及授权分组后进入现有调度器。Redis 的并发、限流、会话、缓存和调度快照仍按原真实账号 ID 工作；新增供应商层级只增加权限/可用性条件，不建立第二套调度器。父级策略撤销需要使整个受影响树的快照失效。

“用户并发”和“上游账号并发”是不同参数：前者控制客户请求额度，后者控制供给账号可承载请求。上述 15/1 仅应用于本次新供应商的上游账号默认值，不能批量覆盖现有运营账号或客户用户配置。

调整入口：供应商管理→供应商编辑→账号创建默认值，影响后续新账号；已存在的供应商上游账号由超级管理员在供应商平台→账号池→选择供应商→编辑中修改并发与优先级；原客户运营后台的平台自有账号沿用既有编辑/批量编辑。一级仅可在其获授权的边界内配置直属二级的创建默认值，不能改子级已有账号。优先级沿用原调度器的排序含义（数值越小越优先）；不能将优先级误当权重或限额。

原生平台自有账号新增弹窗当前默认并发 10、优先级 1；供应商新账号改为 15/1。客户登录用户并发仍由系统设置/用户编辑控制，不受本次修改影响。当前代码的旧供应商默认是 100 / 100 / 3 / 50，截图也与之吻合；这不能证明生产每个账号都用这些值。上线前只读汇总实际账号按平台/类型的并发和优先级分布，差异经确认后再决定是否批量调整，不从截图猜测生产默认。

## 五、平台身份基线核验

保留后端身份归属保护，把批次维护入口归到供应商后台的高级维护，仅超级管理员可用。它核验既有平台账号的可信上游身份，防止供应商以同一 OAuth 根账号重复入池、抢占平台或其他供应商账号；不轮换 Token、不转移归属、不把认证失败当成可重新认领。

既有安装首次开放供应商供给前需要核验旧账号；以后仅处理未核验/失败重试项。无需供应商每天操作，也不应摆在常规开户主流程。已有成功基线沿用，失败清单保留，不能为减少页面控件而删除安全校验。

## 六、实施与验收顺序

1. 明确角色/上下级/双边合同数据契约和迁移。迁移前审查旧 vendor 关联用户；迁移仅将已有 vendor 对应的普通登录用户映射到一级，无父级猜测，不转换无供应商关联的普通客户。安全处理其既有客户权限与会话。
2. 原子开户、默认值、账号角色与权限检查；后台和一级的开户与策略编辑统一服务。
3. 扩展独立站为统一角色工作区，调整导航与代理表单；复用原组件和四语。
4. 补齐父级只读资源范围、祖先停用/授权撤销、用量归属与双边账务隔离。
5. 单元/数据库集成/接口权限/界面验收：同级、跨根、下级越权、只读写接口、并发开户失败回滚、历史账单不变、归档保留、域名隔离、密码不回显、四语/主题/手机。

实施以真实后端与验收证据为准；未实现的环节不通过前端隐藏或原型模拟宣称完成。主工作区有其他调度改动，本次在独立工作树完成并记录合入范围；不覆盖其他任务修改。
