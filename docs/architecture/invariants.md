# Architecture Invariants

这些规则是功能开发不能破坏的系统契约。改变任何一条必须提交新的 ADR、迁移和回滚方案。

## 身份与权限

1. User 是登录、角色、余额和订阅主体。
2. API Key 是调用、配额、权限收窄和统计主体，不是独立登录账户。
3. Key 的有效权限只能是 User/Group 权限的子集，不能扩大上级权限。
4. 普通用户按 Key 查询或修改时必须同时验证 `api_key.user_id = current_user_id`。
5. Channel 是策略维度，Account 是上游凭证维度；两者不能替代 API Key 身份。

## 计费与配额

1. API Key 配额和用户钱包/订阅是独立门禁，两者都必须满足。
2. `quota=0` 的无限 Key 只绕过 Key 总配额门禁，仍累计 `quota_used` 并正常扣除用户资金。
3. 有限配额的并发准入必须使用原子条件更新，不能先读后写。
4. 上游已经产生的正向权威用量必须记录，即使最终金额超过估算。
5. 一个失败尝试最多退款一次；一个已结算请求不得重复扣费。
6. Key 预占失败不能残留用户资金预占，用户资金失败也不能残留 Key 预占。
7. 统计查询和导出只读，不产生二次扣费。
8. `(request_id, api_key_id)` 仍是消费归属和去重的重要复合身份。

## 并发与缓存

1. 用户并发上限覆盖其所有 API Key 的活跃请求总和。
2. Account 并发限制实际发送到单个上游账号的活跃请求数。
3. 普通 API Key 独立并发在未正式启用前只能统计，不能被 UI 误称为强制门禁。
4. 新增 Key 并发必须原子获取，并按 `User → API Key → Account` 顺序管理和逆序释放。
5. Redis 是活跃槽位和缓存基础设施，不是余额、Key 状态或配额的最终权威来源。
6. 请求完成、取消、断开和超时时必须最多释放一次槽位。

## 日志与审计

1. 每条可计费用量必须关联 `user_id` 和 `api_key_id`。
2. 用量事实只追加；修正采用补偿或受控迁移，不静默改写历史。
3. Key 改名、轮换或删除不能让历史归属消失或改变语义。
4. API Key、上游 Key、OAuth Token 和其他凭证明文不得进入用量、错误、审计、导出或应用日志。
5. Key 名称用于展示，身份和权限判断始终使用不可变 ID。

## 失败、迁移与兼容

1. 新状态只有一个权威所有者，兼容双写必须有终止条件和一致性检查。
2. 数据迁移必须定义失败恢复、重试或补偿方式。
3. Feature Flag 关闭后应回到明确的官方兼容行为。
4. 临时兼容层必须记录 owner、移除条件和保护测试。
5. 新协议入口上线前必须通过认证、计费、并发和 API Key 归属合同测试。

## 上游同步

1. 官方仓库只作为 `upstream` 拉取源，本地定制推送到 `origin`。
2. 本地定制不复制整套官方核心模块形成平行实现。
3. 官方出现等价能力时，必须评估迁移和退役本地实现。
4. 合并官方更新后必须重新验证本文件中的关键合同。
